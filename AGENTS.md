# AGENTS.md — Riffuna

## Цель и рабочее дерево

Riffuna — локальный музыкальный плеер для Windows и Android. Основные сценарии — найти нужную запись, быстро её включить, сохранить музыку и вернуться к прослушиванию. Spotify и Яндекс Музыка служат ориентирами для навигации и управления плеером. Источники текущего приложения — YouTube и локальные аудиофайлы. Обычный запуск работает без собственного удалённого сервера.

- Продолжай существующее приложение. Локальный Windows checkout владельца — `C:/Projects/free-spotify`, репозиторий — `NikiChaZi/Riffuna`. Перед правками проверь корень, ветку, незакоммиченные изменения и актуальную задачу. Сохраняй существующие правки и локальные артефакты владельца.
- Используй `shared/` для общей логики очереди, коллекции и музыкального сопоставления. Windows — `desktopApp/`, Kotlin и Compose Multiplatform, libmpv. Android — отдельная Gradle-сборка в `android/`, Compose и Media3. Сетевой код YouTube и его зависимости закреплены в `source-runtime/`; Android JS-компонент генерируется из этого же источника. Python используется для обучения, экспорта и проверок ML. Активный клиент остаётся на Kotlin.
- Начинай с `README.md`, исходников затронутого сценария и `.github/workflows/`. В старых отчётах есть сведения об уже изменившемся поведении. Версию бери из Gradle и сборочных скриптов, факт публикации сверяй с GitHub Releases.

## Поведение, которое нужно сохранить

- **Поиск и версии.** Студийная запись должна находиться по названию и исполнителю. Выдача музыкальная. Клиповые версии, live, реакции, разборы и зацикливания отфильтровывай с учётом метаданных, не выкидывая студийный трек из-за совпадения слова в названии. Релевантные slowed, sped-up, мэшапы, ремиксы и OST остаются доступными. «Другие записи» сопоставляй по названию, исполнителю, длительности, типу версии и доступным метаданным. Надпись «без цензуры» сама по себе не подтверждает содержимое записи. Для регрессий используй примеры из чата по смыслу задачи: Дора, «Карта в блоке» — Главный герой, «Фенибут», «Кайфоград». Живые результаты провайдера меняются.
- **Воспроизведение.** Проверяй фактическое продвижение позиции на новом треке с пустым кэшем, seek кликом и перетаскиванием, паузу, следующий и предыдущий трек. Поиск или успешное разрешение ссылки не подтверждают воспроизведение. При сетевых правках проверь чтение позднего диапазона, восстановление с позиции и отмену устаревшего запроса после смены трека. На Windows отдельно проверь клик после наведения, когда открыта подсказка времени. Раньше подсказка перекрывала полосу и перехватывала нажатие. Треск и щелчки проверяй на реальном аудиовыходе, включая Bluetooth при наличии устройства.
- **Очередь и коллекция.** Сохраняй различие между обычным запуском трека, контекстом воспроизведения и явным добавлением в очередь. Очистка очереди не останавливает текущий трек. Сортировка списка не переписывает порядок плейлиста. Сохраняй лайки, историю, плейлисты, настройки и выбранную версию при обновлении. Для переноса ПК ↔ Android используй существующий JSON-обмен с добавлением данных. Автоматический кэш и явно сохранённый офлайн различаются. Запись доступна офлайн после полного сохранения и проверки без сети.
- **Интерфейс и тексты.** Сохраняй графитовые поверхности, тёплый текст, коралловый акцент, реальные обложки и режим уменьшенного движения. Избегай фиолетовых тонов и декоративных градиентов. Android проверяй в портретной ориентации. Применяй точные таймкоды слов только к той редакции записи, для которой они проверены. Если доступен только построчный LRC, обозначай расчётную подсветку слов. При рассинхронизации исправляй сопоставление и тайминг в коде.
- **Платформы.** Держи общие правила каталога и очереди согласованными между Windows и Android. Проверяй системное управление там, где оно затронуто: на Windows — медиаклавиши при свёрнутом окне, на Android — `MediaSessionService`, шторку, заблокированный экран и длительное воспроизведение в фоне. Samsung Now Bar проверяй на физическом устройстве, когда оно доступно. Эмулятор не подтверждает поведение One UI и Bluetooth.
- **«Резонанс».** Это отдельные музыкальные Two‑Tower и CatBoost с локальным ONNX-инференсом на Windows. Существующие серверные компоненты другого recsys-проекта (Qdrant, Redis и мониторинг) не являются зависимостями плеера. При изменениях моделей сверяй `docs/music-recsys.md` и `docs/music-evaluation.md`, измеряй покрытие каталога и сравнивай с бейзлайнами на том же разбиении. Для Windows-упаковки сохраняй подготовленные артефакты `build/kotlin-music-model`.

## Спецификации и ревью

- Для заметного изменения сначала запиши короткую спецификацию с критериями приёмки. Храни её в Issue или в отдельном файле задачи, например в docs/tasks/. Этот файл содержит постоянные инструкции проекта.
- Для изменений сети, хранения данных, подписей и обновлений проведи отдельное ревью diff. Проверь, какие данные уходят из приложения и попадают в логи или сборки, что может потеряться при обновлении, импорте и сбое, и как восстанавливается операция.
- Перед релизом проверь установку поверх предыдущей версии на тестовом профиле с данными. Подтверди, что сохраняются библиотека, выбранные записи, настройки и очередь.
- Для приватности сверяй docs/data-flows.md с фактическим кодом. Проверяй пакеты и отчёты до загрузки. Используй синтетический профиль, не записывай токены, подписанные URL или локальные пути в диагностику.

## Сборка, проверка и передача результата

- Проверки запускай из корня. Выбирай по изменению и доводи до реального сценария. За изменением общего ядра проверяй обе платформы. Живые проверки YouTube запускай отдельно от обычных тестов. При недоступной сети, устройстве или аудиовыходе напиши, что именно не получилось подтвердить.

  ```powershell
  # Windows и общее ядро, как в CI
  .\gradlew.bat spotlessCheck :shared:jvmTest :desktopApp:test

  # Android, при подготовленных SDK и JS-компоненте
  .\gradlew.bat -p android spotlessCheck :core:testAndroidHostTest :app:testDebugUnitTest :app:lintDebug :app:assembleDebug

  # Проверка Android bundle после изменений source-runtime
  node scripts/build_android_source.mjs --check
  ```

- Для Windows-поставки используй `scripts/build_kotlin.ps1`, для живой проверки — его параметр `-LiveTest`. Когда владелец просит обновить привычный EXE, после проверки запусти `scripts/install_kotlin.ps1` и проверь конкретный запуск `Riffuna.exe` с соседним `Riffuna.runtime`. Для тестов с данными запускай Windows-клиент с `MUSICDESK_DATA_DIR`, указывающим на отдельный тестовый профиль. Обычный запуск использует `%USERPROFILE%\.riffuna` независимо от папки EXE.
- Для Android используй `scripts/build_android.ps1` и `docs/android-mvp.md`. Для тестов бери debug или существующую изолированную тестовую сборку. Сохраняй пакет `app.riffuna.player` и подпись обновляемого APK, проверяй SHA‑256. Сборки, ключи, пользовательская библиотека, кэш и данные обучения не коммитятся. Установка не должна очищать данные или удалять отдельный пакет Riffuna Tests.
- По задаче на релиз проверь нужные сборки, совместимость обновления поверх предыдущей версии, версии и SHA‑256, затем CI и доступность артефактов. Выпуск отдельной версии — самостоятельная задача. Публикуй, когда это входит в текущее поручение. Сохраняй PolyForm Noncommercial 1.0.0 для актуального собственного кода и уведомления зависимостей. Перед добавлением внешних материалов сверяй `LICENSING.md` и `THIRD_PARTY_NOTICES.md`.
- В отчёте укажи, что изменилось для пользователя, какие команды и сценарии реально прошли, на какой платформе и сборке. Для артефакта укажи путь и версию. Для опубликованного изменения добавь ссылку на коммит или релиз и итоговый статус CI.
